## Misses

None against the expectations. No reply in this run went wrong because of a skill line.

Two places in the diff give opposite instructions, though, and this run passed only because it chose one of them. A different run could follow the other. Both are wording fixes and both should go in before release.

1. **Record the held-back roles, or not?** `find-jobs` Step 6: "Run `record(cards)` from `references/scan-history.md` on every STRONG and INCLUDE role, the ones shown and the ones held back as seen." Step 4b agrees: "classify it in Step 5 with the rest (so its tier is current when the scan is recorded)." But `scan-history.md` says the opposite: "Record only the cards the scan showed. A role `seen_before` left out keeps its old date, so if it's still posted after 30 days, it shows once more." The `record()` docstring ("Save the cards this scan showed") and "The two calls" ("the cards the user was shown") side with the reference. This run followed Step 6, because it's the step that makes the call, and case 3's expected dates follow it. A run that followed the reference would leave the held-back rows at Oct 24, and they would come back as new 30 days after they were first shown, while still posted. The two readings are two different products. Smallest fix, if Step 6 is the intent (it matches the CHANGELOG and the tested behavior): in `scan-history.md`, replace that paragraph with "Record every STRONG and INCLUDE card the scan found, the ones shown and the ones held back, so a role stays out of 'new' while it's still posted; one the scans stop finding drops off after 60 days," and change "Save the cards this scan showed" and "the cards the user was shown" to match.
2. **"The date each was last shown" isn't in the file.** Step 4b: "If the user asks to see the held-back roles ('show them'), list them with the date each was last shown." But with held-back roles re-recorded, `date_seen` becomes the last date a scan found the role, held back or shown, while the column note still says "`date_seen` is the last date a scan showed the role." Case 4 passed because the reply used the dates `seen_before` printed before `record()` ran. A probe after `record()` printed "shown 2026-10-31" for all 7, and a probe of a third weekly scan (Nov 7, with no "show them" in between) printed "shown 2026-10-31" for 7 roles Sam last saw on Oct 24. Smallest fix: in Step 4b, "list them with the date `seen_before` printed for each, the last date a scan found it," and the same words in the column note. ## Still open

Wording and code risks, most important first, each with the smallest fix:

1. **A history whose header is intact but whose rows ran together is read as one row, and the next record overwrites it.** Not in the brief; found with a probe of case 6's neighbor. The header check catches rows that ran into the header, but with the header on its own line and the rows glued together, `csv` reads one row with the rest in extra fields: no CAN'T READ line, 6 already-seen roles came back as new, and `record()` rewrote the file from that one row plus the scan's cards, so Tidewell's row and every old date were lost. It's only the scan history, but it's silent. Smallest fix, in `read_history()`: treat any row with more fields than the header (`None in r`) as unreadable, which raises the CAN'T READ path and leaves the file alone. The tracker's `load()` has the same gap, and it matters more there: a probe with the header on its own line and three rows glued together read 1 row with no error, so the next save would drop the other two. That's older code, outside this diff.
2. **An unreadable history stays unreadable.** Every later scan will say "I couldn't read your scan history" and record nothing, and no line says what to do about it. Smallest fix: "If it can't be read on a later scan too, offer once to set it aside as `scan-history-unreadable.csv` and start a new one."
3. **"Strong only" would record roles the user never saw.** Step 6 records "every STRONG and INCLUDE role," but with pickiness "strong only," INCLUDE roles are neither shown nor held back; they're counted. They'd be held back for 30 days if the user switched to "strong plus maybe." Not tested. Smallest fix: "every STRONG and INCLUDE role the user was shown or that was held back."
4. **The saved-search worked example is Sam's case and now disagrees with the new lines.** `building-a-saved-search.md`: "A senior PM, NYC metro, remote or hybrid" gives `f_E=4` and `location=New%20York...&f_WT=2,3`, while the new lines say Group PM targets need `f_E=4,5` and remote anywhere in the US needs `location=United%20States` with `f_WT=2` plus a city search with `f_WT=3`. This run followed the new lines, but a reader matching on the example would build the old URL. Smallest fix: make the worked example the two-search version. Existing profiles also keep their old URL; Sam's current search misses Director-tagged Group PM roles and nothing will say so.
5. **No limit when a user needs both a second title and a second place.** Setup says "Add a second only for a title or a place the first misses," and the new line adds a city search. Jordan's variant needed both (delivery manager titles, and hybrid near Raleigh). This run built three searches and left out a fourth. Smallest fix: "With both, keep the title search remote and the city search for the main title."
6. **Where `PM_MEANS` comes from, in the rubric.** "Checking against the tracker": "`pm` to whatever the tracker's `PM_MEANS` says, product manager by default." The rule that sets it from the profile's target titles is only in `tracker-schema.md` rule 1, and a reader in `find-jobs` could take the snippet's default line as what the tracker "says." It held here. Smallest fix: "`pm` to the `PM_MEANS` set from the profile's target titles (see rule 1 of 'Matching a role' in `tracker-schema.md`)."
7. **The skipped-source fallback reads like a second ask.** For job site searches with no browser, the skill says "hand over the link to click and paste back," and `ats-feeds.md` says to "offer the board links." The replies here ended the links line with "Paste anything you find and I'll sort it the same way," above the one offer. It's what the skill asks for, but "End with at most one offer" doesn't say whether it counts. Smallest fix: "Handing over the links for a skipped source isn't an offer." The same two files also label an unreachable watchlist differently ("not available here" in `ats-feeds.md`, "skipped (reason)" in Step 6); this run used the second.
8. **Name-only matches on generic names.** `same()` falls back to company and title when the links differ, so a second "Confidential Company: Senior Product Manager, Growth" from a different employer within 30 days would be held back. It would still be counted in "Also held back." Smallest fix: skip the name match when the company name is "Confidential" or similar.
9. **Roles back after 30 days are called "new."** Scan 3's "9 new roles" were all roles Sam had seen in October, and nothing said so. Smallest fix: "A role last found more than 30 days ago is shown with 'seen in an earlier scan, Oct 31.'"
10. **Smaller.** CAN'T READ printed twice, once in Step 4b's run and once in Step 6's, because each is its own `.py` file and `WARNED` lasts one run; the reply said it once, as Step 4b asks. The scheduled scan prompt doesn't record what its digest showed, so those roles come back as new in the next scan at the computer; that's reasonable for a digest the user may not have read, but no line says it. The prompt's source words ("worked, 0 results, failed, or skipped (no browser)") have nothing for a watchlist the task can't reach; 9b used "failed." The prompt doesn't say to compare names the way the tracker does; this run used the snippet's `seen_before`, which only reads.
