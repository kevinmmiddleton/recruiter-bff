## Misses

1. **(1) Every blind run repaired the user's tracker itself.** The brief and the CHANGELOG say the plugin "stops and says how to fix it." The main run did that, ending with one offer to fix it ("Or I can put the line breaks back for you with Python, changing nothing else. Want me to?"). All four blind runs got the right CAN'T READ line, then wrote their own Python to split the rows or re-quote the location, saved over the user's file, reran the update, and told the user afterward ("One thing I fixed first..."). The line behind it, in the `load()` message in `tracker-schema.md` (and the same words in `contacts-schema.md`): "Fix the copy so each row is on its own line and any comma inside a value is in quotes, then run this again. Never write this copy back." It's written for the cloud flow, where the shell works on a copy. Here the shell read the user's own file, and all four readers took "fix the copy" to mean "fix the file the snippet read." Two said a stop-and-ask reply "would also be defensible." Nothing else in the skill says what to tell the user. The repairs were careful (backups, value counts, column checks), and three of the four final trackers are byte-identical to the main run's after the user fixed it by hand (`d7f12ff5...`), so nothing was lost here. But it's a guess on the user's own data, and a comma in a notes field or rows with filled `next_date` values would make the guess harder. One root cause, counted on four checks (the bytes and the reply, for each damage). Smallest fix, in `application-tracker/SKILL.md` under "Saved from a spreadsheet app" (and the same line in `contacts`): "If a snippet says a row has more values than the header, don't repair the user's file yourself: say which row looks wrong, how to fix it (each row on its own line, any comma inside a value in quotes), and run the snippet again when they say it's done." If the intent is that Claude repairs it, the fix is the reverse, and it needs guardrails: "only when every extra value has one clear place; show the row before and after, and keep a copy."
2. **(2) The set-aside offer and the tracker offer in one reply.** The main run made the set-aside its one offer and left the tracker for later. Both blind runs wrote the set-aside as a line under the history notice ("Say 'set it aside' and I'll rename it...") and still ended with "Want me to add the strong ones to your tracker?" Both flagged the conflict. The lines: find-jobs Step 4b, "offer once to set the unreadable file aside (`set_aside()`)," against Step 7, "Make **one** offer per message," and "End with at most one offer." Nothing says whether a "Say ..." line counts. Smallest fix, in Step 4b, either "That's the reply's one offer; the tracker offer waits," or (what both readers did, and probably the better product, since the tracker is what keeps roles from coming back) "Put it as one 'Say "set it aside"' line under the history notice, like 'show them'; that line isn't an offer."

## Still open

Wording risks, most important first, each with the smallest fix. Each passed here.

1. **Two labels for an unreachable watchlist.** find-jobs Step 6: a source that can't run "isn't a failure: label it 'skipped' with the reason." `ats-feeds.md`: 'mark the watchlist "not available (no web access)".' Every interactive reply used "skipped (no web access)"; both scheduled runs used "not available (no web access)," which the prompt lists. Two blind readers flagged it. Smallest fix: in `ats-feeds.md`, "mark the watchlist 'skipped (no web access)' in an interactive scan (the scheduled prompt says 'not available (no web access)')," or use one label in both.
2. **The headline when every role is back from an earlier scan.** "The headline counts what's shown. The first number is every new role on the list." On Nov 28 every shown role was tagged "Shown Oct 24, still open," so "8 new roles" would contradict the tags; the main run wrote "8 roles, 5 of them strong, all back from your Oct 24 scan; nothing brand new today." Smallest fix: "Count roles tagged 'Shown ..., still open' as 'back from an earlier scan,' not as new."
3. **When to record after a set-aside.** All three readers ran `record()` on the scan's roles right after `set_aside()`, which is right: otherwise next week shows them all as new. But `scan-history.md` says "so the next record starts a new history" and Step 4b says "so the next scan starts a fresh history," which read like waiting. Smallest fix: "then run `record()` on the roles this scan showed."
4. **A scheduled digest that asks for a reply.** The 9a blind digest ended "Say 'show them' to see them" and "Want me to add the two strong ones to your tracker?" Whether a user can answer inside a scheduled run wasn't checked. If not, smallest fix in the prompt: "End without an offer; to act on these, say 'scan for jobs' at your computer."
5. **"Stealth Startup" is a shared placeholder name.** `same()` matches on company and title when there's no link, so a different stealth startup's "Senior Product Manager, Lifecycle" within 30 days would be held back. Run 10a's item 8 raised this for "Confidential Company," which is now excluded; "Stealth Startup" inherits it. Smallest fix: "A company named only 'Stealth Startup' or 'Stealth' matches by link only."
6. **"our client" sits in two rules.** The staffing rule counts a posting that mentions "on behalf of our client" as probably staffing; the confidential list names "our client." With "Include confidential postings," both runs showed the card, and the blind reader flagged the overlap. Smallest fix, in the staffing rule: "A company line that reads 'our client' is a confidential posting; see below."
7. **Confidential fit checks share a folder.** Every confidential posting goes to `companies/confidential-company/`, so two unrelated employers end up as `job-post.md` and `job-post-<role>.md` side by side. Low.
8. **Existing profiles don't show the new default.** A 1.0.2 profile's Company types line doesn't mention confidential postings, and they're still hidden (all three runs). Correct, but a user reading their profile won't see why; the CHANGELOG says it. Low.

Not tested: a browser; the watchlist over a real network; links in the history or tracker (every pasted card had none); a stray comma whose place is ambiguous, such as one in `notes`; `contacts.csv`'s run-together check; a history edited in Excel; and anything in a real Cowork session. The Oct 31 and Nov 28 pastes reuse Oct 24's cards, which a past-week search wouldn't return.
